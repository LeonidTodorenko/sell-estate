# Iteration 26.1: миграция паролей

Выполнять только из `C:\App`. В `C:\Data\sell_estate\sell-estate` хранятся только перенесённые исходники; запускать проект оттуда нельзя.

Этот проект не запускает основной backend, фоновые задания или почту. Соединение передаётся через `PASSWORD_MIGRATION_CONNECTION`; не указывайте секреты в аргументах и отчётах. Без `--apply` выполняется только подсчёт записей.

Перед применением создать свежий CUSTOM pg_dump, проверить SHA-256, восстановить архив в отдельную БД UTF-8 с `--no-owner --no-privileges --exit-on-error` и выполнить регрессионные проверки. Сам инструмент проверяет только совпадение хеша файла, а не факт его восстановления.

Пример последовательности (соединение задаётся приватно в окружении):

```powershell
Set-Location C:\App
dotnet run --project RealEstateInvestment.PasswordMigration
# После подтверждённого восстановления бэкапа:
dotnet run --project RealEstateInvestment.PasswordMigration -- --apply --verified-backup C:\App\work\YOUR-VERIFIED.dump --sha256 YOUR_SHA256 --demo-legacy-format factory-sha256
```

Параметр `--demo-legacy-format` требует отдельного выбора по происхождению данных:

- `factory-sha256`: исторические demo-пароли фабрики (Base64 SHA-256) оборачиваются в солёный PBKDF2. После успешного demo-login заменяются прямым PBKDF2 исходного пароля. Значения других форматов считаются plaintext.
- `plaintext`: все старые demo-значения считаются исходными паролями.
- `skip`: demo-записи не менять; их формат нужно разобрать отдельно.

Автоматически отличить произвольный plaintext из 44 Base64-символов от старого SHA-256 невозможно. В восстановлении Iteration 26.1 обнаружены две записи demo фабричного формата. Для другого набора данных сначала проверить происхождение и выбрать режим; не угадывать смешанные неоднозначные значения.

Обычные исторические аккаунты использовали plaintext. Они переводятся в солёный PBKDF2 (ASP.NET Identity V3, 210000 итераций) без изменения исходного пароля. Новые регистрации, admin-create/reset, user-reset/change и development bootstrap сразу сохраняют хеш. Login старых аккаунтов поддерживается на переходный период и обновляет хеш при успехе. PIN и финансовые условия не меняются.

Изменения применяются одной транзакцией с compare-and-swap по старому PasswordHash: параллельный reset не перезаписывается. Несовпадение количества обновлений означает, что нужно повторить dry-run и проверить оставшиеся строки. Повторный запуск идемпотентен.

Сначала развернуть совместимый backend, затем применять миграцию. Старый backend не умеет проверять новые хеши; откат только к старому коду несовместим с мигрированными паролями. Предпочтителен forward fix. Полное восстановление БД допустимо только по отдельному плану с учётом всех записей после снимка.

В Iteration 26.1 миграция применена только к локальному восстановлению. На сервере её не запускали. Развёртывание backend и серверная миграция требуют отдельного согласования.
